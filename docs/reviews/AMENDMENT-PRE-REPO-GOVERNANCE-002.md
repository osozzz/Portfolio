# Pre-Repository Governance Amendment 002

## 1. Purpose

Record the owner-approved repository-governance decisions made immediately before GitHub bootstrap so implementation starts with the intended human ownership, project-management and documentation model.

## 2. Approved decisions

### 2.1 Human issue ownership

Implementation Issues default to **Alejandro** as the accountable human assignee unless he explicitly assigns another human collaborator.

Automation may create checks, status updates or maintenance PRs where appropriate, but it is not the project owner and does not become the accountable assignee for product implementation work.

### 2.2 Authorship and attribution

The portfolio remains human-owned. Development tools, generators, IDEs, assistants and automation services are tools, not creative authors/co-authors.

Repository-visible and public project surfaces must not add tool-authorship/provenance credit such as:

- `Made with <tool>`;
- `Built by <tool>`;
- `Generated by <tool>`;
- `Co-authored-by: <tool/bot>`;
- badges or credits whose purpose is to attribute creative authorship to development tooling.

This rule applies to README, Wiki, public site, Making Of/Credits, changelog, release notes, commit trailers, PR metadata used as permanent authorship, source comments used only as provenance advertising, package/project metadata and controllable generated-artifact metadata.

Operational service/bot identities may appear where technically unavoidable, but never as creative authorship/ownership.

### 2.3 Tool-specific local configuration

The committed repository stays tool-neutral. Tool-specific operator instruction files may exist locally for Alejandro but remain outside version control using local exclude/global ignore mechanisms.

DOC-19 is renamed/reframed as the committed, tool-neutral source of implementation-tooling, automation and authorship governance.

### 2.4 GitHub Project

The GitHub Project is required during V0 repository bootstrap. It is the execution view, not the product specification source.

Baseline workflow:

```text
Backlog
Ready
In Progress
Review
Blocked
Done
```

Recommended fields:

- Release;
- Priority;
- Area;
- Risk.

### 2.5 GitHub Wiki

The GitHub Wiki is required as a **human-friendly, non-canonical companion layer**.

Baseline pages:

```text
Home
Start Here
Project Overview
Roadmap
Architecture at a Glance
Design System at a Glance
Local Development Quickstart
Release & Deployment Guide
Troubleshooting
Useful Links
Glossary
FAQ
```

Wiki rules:

- `/docs` + approved ADRs remain canonical;
- Wiki pages summarize and link to exact canonical sources;
- the Wiki cannot independently introduce product/architecture decisions;
- avoid duplicating large canonical specifications;
- Wiki content follows the same human-authorship/attribution policy;
- Wiki language may be friendlier and more onboarding-oriented than canonical specifications.
