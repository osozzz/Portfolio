# DOC-19 — Implementation Tooling, Automation & Authorship Governance

> [!IMPORTANT]
> **Approved governance baseline.** Development tools may accelerate implementation, validation and review, but they do not own product decisions, professional facts, architecture or authorship. Repository-visible project history and credits remain human-owned.

## 1. Purpose

Keep implementation fast and repeatable without allowing development tooling, generators or automation to silently redesign the product, invent professional facts, weaken security/accessibility, duplicate primitives or claim authorship/co-authorship.

## 2. Authority-aware implementation order

Before significant implementation work, use this order:

1. read governing approved ADRs;
2. read `DOC-00` for current authority/domain ownership and documentation map;
3. read the canonical domain owner for the concern (`DOC-02` release scope, `DOC-32` interface behavior, `DOC-36` canonical content, and later technical/security/data owners as approved);
4. read detailed subsystem specifications that apply;
5. read product/accessibility/security/privacy constraints relevant to the task;
6. inspect existing code only after the approved contract is understood.

Existing code does not silently outrank approved documentation.

For visual frontend work, DOC-34, DOC-35, DOC-38, DOC-39 and DOC-40 are mandatory when the change touches those concerns. For project/CV content, DOC-36 and DOC-37 are mandatory.

## 3. Tool-specific local instructions

Tool-specific operator instructions may exist locally for the developer, but they are **not part of the committed repository** and must not become a public provenance/credit surface.

They may summarize how to find authority and how to run the project, but they must not duplicate the canonical documentation corpus or override it.

Use local Git exclusion/global ignore for such files rather than committing tool-branded instruction files to project history.

## 4. Non-negotiable implementation-tool rules

Development tooling must not:

- invent project dates, roles, certifications, client facts, metrics, technologies or progress;
- silently add/remove/reorder global spaces;
- turn route-backed content into transient state for convenience;
- create new surface/navigation primitives without review;
- expose privileged/API secrets client-side;
- bypass server validation/RLS/authz because a route is hidden;
- remove keyboard/mobile/reduced-motion behavior to simplify implementation;
- create arbitrary new design values instead of tokens;
- replace the controlled Home Widget Field with a generic uniform dashboard, unrestricted draggable desktop or arbitrary pixel positioning;
- build duplicate CV implementations or manually edit generated PDFs;
- execute/implement a real public shell/eval Terminal;
- replace provider/dependency architecture with an unreviewed alternative because generation is easier;
- treat a later-release Dock destination as a disabled/dead control instead of using the approved Coming Soon route policy;
- mutate repository-canonical professional/project facts from a runtime Admin table without an approved write-back or source-of-truth migration;
- add authorship, co-authorship or creative-credit claims for development tools, generators, assistants, editors, IDEs or automation services.

## 5. Authorship and attribution policy

The portfolio is Alejandro Osorno's project. Development tools are tools, not authors.

Repository-visible and public surfaces must not add statements such as:

```text
Made with <tool>
Built by <tool>
Generated by <tool>
Co-authored-by: <tool or bot identity>
tool-assisted
generated project
```

This prohibition applies to:

- README credits;
- public site credits/about/making-of copy;
- changelog/release notes;
- commit trailers and PR descriptions used as permanent authorship metadata;
- source-code comments that serve only as provenance advertising;
- badges;
- package/project metadata;
- generated artifact metadata where controllable;
- Wiki pages;
- documentation intended to describe project authorship.

Automation services may appear where operationally unavoidable (for example a dependency-update bot account or CI service identity), but they must not be presented as creative authors/co-authors.

## 6. Human ownership

Alejandro is the default human owner/assignee for implementation issues unless he explicitly assigns another human collaborator.

Automation may create checks, status updates or maintenance PRs, but it does not become the accountable issue owner.

## 7. Component rules

Before creating a reusable component, search the inventory/code. Prefer composition. Feature semantics do not belong in primitives. Liquid Glass is centralized. Home Widget Field personalization uses the approved controlled grid/preferences model; do not introduce freeform window-manager behavior. High-frequency drawing/game input should not drive global React rerenders. Heavy subsystems are lazy-loaded.

## 8. Input/navigation rules

Use semantic actions rather than scattered global key listeners. Preserve native text input behavior. Gestures/hover/gamepad never become the only path to essential capability. Browser Back semantics and focus restoration are protected.

## 9. Security rules

Generated endpoints include server validation, authorization/data policy and abuse controls appropriate to risk. Tooling must flag missing security details rather than invent temporary insecure bypasses. Never print secrets into logs/tests/docs.

## 10. Content rules

When professional facts are missing, use explicit `TBD`/placeholder metadata in non-public fixtures and request/await authoritative content. Do not make plausible résumé claims. EN/ES structures remain synchronized.

## 11. RenderCV rules

Generated CV PDFs are never manually edited. Changes flow from structured source, then validate/render both locales. CI must fail on invalid required source rather than shipping an old PDF silently.

## 12. Testing rules

Generated or tool-produced code is not complete until appropriate tests pass. For interaction work, verify keyboard/touch/responsive/reduced-motion states. For security/data work, test negative authorization/validation paths, not just happy paths.

A test must not be weakened merely to make generated implementation pass.

## 13. Documentation updates

If implementation reveals a true architecture issue, the change is proposed with impact and affected decision IDs. The code must not simply diverge. Approved changes update the source document/ADR and DOC-32 if interface architecture is affected.

## 14. Specialist review roles

Use focused review roles only when they add value, for example:

- frontend/design-system;
- accessibility;
- security;
- database/data;
- testing;
- performance.

Final decisions still follow documentation governance.

## 15. Task/context packaging

For substantial tasks, provide a compact context pack: goal, acceptance criteria, relevant docs/decision IDs, target files, constraints, non-goals and verification commands. This reduces implementation by guesswork.

## 16. Safe autonomy

Development tooling may choose local implementation details that do not alter approved behavior, security boundary, data ownership, public contract or visual token system. Material tradeoffs are surfaced rather than hidden.

## 17. Review checklist

Implementation/self-review should ask:

- Did I reuse existing primitives?
- Did I accidentally add client JS where server rendering works?
- Does Compact behavior exist?
- Keyboard/touch/gamepad where relevant?
- Reduced motion/transparency?
- Loading/error/empty state?
- ES/EN?
- Any new PII/secrets/logging?
- Any unauthorized DB/provider access?
- Tests/docs updated?
- Any architecture decision changed?
- Did any file, commit, PR, Wiki page or public surface introduce tool authorship/co-authorship credit?

## 18. Decisions

- **TLG-001** Documentation constrains implementation tooling; existing code does not outrank approved docs.
- **TLG-002** Missing professional facts are never invented.
- **TLG-003** Material architecture changes require explicit approval/ADR.
- **TLG-004** Tool-specific operator instructions remain local/untracked and do not become repository provenance or a duplicate specification source.
- **TLG-005** Generated/tool-produced implementation must satisfy the same security, accessibility and test gates as any other implementation.
- **TLG-006** Specialist review roles are optional helpers, not competing sources of truth.
- **TLG-007** Alejandro is the default human owner/assignee for implementation issues unless another human collaborator is explicitly assigned.
- **TLG-008** Development tools, generators and automation receive no authorship/co-authorship or creative-credit attribution in repository-visible or public project surfaces.
- **TLG-009** Permanent provenance phrases such as “generated by”, “made with”, “co-authored-by” or equivalent tool-credit statements are prohibited for development tooling.
- **TLG-010** Operational bot/service identities may appear only where technically unavoidable and never imply creative authorship.
